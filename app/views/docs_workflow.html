Authentication Workflow

This is the intended authorization-code flow between a client project, Sorkos Login, and the selected OAuth provider.

1. Client Redirects To Sorkos Login

The client project creates a random state, stores it in its own local session, and redirects the user to /authorize.

{{ @request_origin }}/authorize?client_id=example-id&redirect_uri=https%3A%2F%2Fclient.example%2Fauth%2Fcallback&response_type=code&state=example-state&lang=en
Client redirect examples 
<?php
session_start();

$state = bin2hex(random_bytes(32));
$_SESSION['sorkos_oauth_state'] = $state;

$params = http_build_query([
    'client_id' => 'example-id',
    'redirect_uri' => 'https://client.example/auth/callback',
    'response_type' => 'code',
    'state' => $state,
    'lang' => 'en',
]);

header('Location: {{ @request_origin }}/authorize?' . $params);
exit;
import crypto from 'node:crypto';

app.get('/login', (req, res) => {
  const state = crypto.randomBytes(32).toString('hex');
  req.session.sorkosOAuthState = state;

  const params = new URLSearchParams({
    client_id: 'example-id',
    redirect_uri: 'https://client.example/auth/callback',
    response_type: 'code',
    state,
    lang: 'en'
  });

  res.redirect(`{{ @request_origin }}/authorize?${params.toString()}`);
});

2. Sorkos Login Validates The Request

Sorkos Login checks that the client exists, is active, uses response_type=code, and that the redirect URI is an exact registered match.

3. User Signs In With A Provider

If there is no central Sorkos Login session, the user chooses an enabled provider. The first implemented provider is E-Mail, which sends a six-digit one-time code through Sorkos Login's internal browser provider flow. Google and Discord remain configured placeholders until their external OAuth callbacks are implemented.

If a central Sorkos Login session already exists, Sorkos asks the user to continue as the current account before returning to the client. A client can opt into the previous silent SSO behavior with prompt=none.

4. Sorkos Login Redirects Back To The Client

After successful authentication, Sorkos Login creates a short-lived authorization code and redirects the user back to the original client callback.

https://client.example/auth/callback?code=example-code&state=example-state

If the user backs out of the Sorkos flow, the callback receives error=access_denied with the original state.

https://client.example/auth/callback?error=access_denied&state=example-state
Callback validation examples 
<?php
session_start();

$returnedState = $_GET['state'] ?? '';
$expectedState = $_SESSION['sorkos_oauth_state'] ?? '';

if ($returnedState === '' || !hash_equals($expectedState, $returnedState)) {
    http_response_code(400);
    exit('Invalid state');
}

if (($_GET['error'] ?? '') === 'access_denied') {
    exit('Sign-in cancelled');
}

$code = $_GET['code'] ?? '';
app.get('/auth/callback', (req, res, next) => {
  const returnedState = req.query.state || '';
  const expectedState = req.session.sorkosOAuthState || '';

  if (!returnedState || returnedState !== expectedState) {
    res.status(400).send('Invalid state');
    return;
  }

  if (req.query.error === 'access_denied') {
    res.send('Sign-in cancelled');
    return;
  }

  const code = req.query.code || '';
  next();
});

5. Client Exchanges The Code Server-Side

The client validates the returned state, then posts the authorization code to /token from its server. The client secret authenticates the project, and the one-time code identifies the Sorkos user who completed the browser flow. If valid, Sorkos Login returns normalized user information plus an opaque client_session_token, and creates or refreshes the user-client connection with the approved scope and latest-use timestamp.

Token exchange examples 
<?php
$response = file_get_contents('{{ @request_origin }}/token', false, stream_context_create([
    'http' => [
        'method' => 'POST',
        'header' => "Content-Type: application/x-www-form-urlencoded\r\n",
        'content' => http_build_query([
            'grant_type' => 'authorization_code',
            'code' => $code,
            'client_id' => 'example-id',
            'client_secret' => 'example-secret',
            'redirect_uri' => 'https://client.example/auth/callback',
        ]),
    ],
]));

$tokenResult = json_decode($response, true);
const response = await fetch('{{ @request_origin }}/token', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/x-www-form-urlencoded'
  },
  body: new URLSearchParams({
    grant_type: 'authorization_code',
    code,
    client_id: 'example-id',
    client_secret: 'example-secret',
    redirect_uri: 'https://client.example/auth/callback'
  })
});

const tokenResult = await response.json();

6. Client Creates Its Own Local Session

The client creates its own local session and stores the returned client_session_token with it. Sorkos Login does not share cookies across projects and does not write sessions for client applications.

Optional recurring check: a confidential client with long-lived sessions can periodically post its client credentials and that token to /client/sessions/introspect. If the response is {"active":false}, destroy the matching local session and require authentication again. A short positive-result cache is recommended instead of checking on every request; security-sensitive actions may check immediately.

The central Sorkos browser session and the client-owned session deliberately have separate lifetimes. Expiry or logout of the central browser session alone does not invalidate the client's token. Explicit invalidation in the Sorkos account UI, disconnecting the client, disabling the user, or disabling the client does.

7. Client Handles Logout

Default product logout: the client destroys only its own local product session. It must not call or redirect to the Sorkos Login /logout endpoint. The central Sorkos Login session remains active so the user can continue using SSO in this and other products.

Special case — explicit Sorkos logout: only when the product deliberately offers an action that signs the user out of Sorkos itself should it clear its local session and then redirect the browser to /logout. Do not use this endpoint for a normal product logout. A supplied redirect_uri is only used when it exactly matches a registered URI for the supplied client_id.

{{ @request_origin }}/logout?client_id=example-id&redirect_uri=https%3A%2F%2Fclient.example%2Fauth%2Fcallback

Optional all-device revocation: a client that can revoke all of its own sessions for one user may implement the signed endpoint defined in the client endpoint contract. Once that endpoint is registered for the project, Sorkos offers “Log out on all devices” on the client's account page. Clients without this capability expose only Auth-side invalidation.

8. Client Completes Project Account Deletion

A client may provide its regular account-deletion page for the Sorkos account UI to link to. The link contains no added parameters; authentication and deletion remain entirely under the project's control.

After the project has deleted its own user account and data, its server posts the public Sorkos user ID to /client/connections/revoke. The client authenticates with its own ID and secret. The idempotent request removes only this project connection and never deletes the central Sorkos account.

POST {{ @request_origin }}/client/connections/revoke
Content-Type: application/x-www-form-urlencoded

client_id=example-id&client_secret=example-secret&user_id=usr_example
