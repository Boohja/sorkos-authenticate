Implement the Sorkos client endpoints

Use this contract when adding Sorkos Login support to a project. Your client must implement the login callback. It may also expose endpoints that let Sorkos Auth revoke all local sessions or delete a local user.

No handshake is required. For direct server requests, derive a signing key from the client secret already issued to your project. Sorkos Auth will not call a client endpoint without a valid signature.

Verify direct requests from Sorkos Auth

Apply this verification to every machine endpoint described below. Derive the signing key as a lowercase hexadecimal string:

signing_key = SHA-256(client_secret)

Each direct request from Sorkos Auth contains these headers:

X-Sorkos-Client-Id: example-id
X-Sorkos-Timestamp: 1789570000
X-Sorkos-Nonce: 48f8c4e9d7024df4a251851f214bdc88
X-Sorkos-Signature: v1=<hex-hmac-sha256>

Recreate the HMAC input as UTF-8 text with exactly these newline-separated fields:

v1
POST
/auth/sorkos/sessions/revoke
1789570000
48f8c4e9d7024df4a251851f214bdc88
<lowercase SHA-256 hex of the exact request body>

Compute v1=HMAC-SHA256(signing_key, canonical_input). Use the 64-character hexadecimal signing key exactly as written; do not hex-decode it before using it as the HMAC key.

Reject the request unless all checks pass

  • The timestamp differs from your server time by no more than 300 seconds.
  • Atomically reject a nonce that was accepted before, then store it until at least signed_timestamp + 300 seconds. With maximum positive clock skew, this can be almost 10 minutes from receipt.
  • The body hash was calculated from the exact raw bytes received, before JSON decoding.
  • The signed request target equals the URL path plus its query string, if present.
  • The signature matches using a constant-time comparison such as hash_equals.
  • X-Sorkos-Client-Id is your project's assigned client ID.

Expose production endpoints only over HTTPS.

PHP verification example 
<?php
$body = file_get_contents('php://input');
$timestamp = $_SERVER['HTTP_X_SORKOS_TIMESTAMP'] ?? '';
$nonce = $_SERVER['HTTP_X_SORKOS_NONCE'] ?? '';
$provided = $_SERVER['HTTP_X_SORKOS_SIGNATURE'] ?? '';
$clientId = $_SERVER['HTTP_X_SORKOS_CLIENT_ID'] ?? '';
$requestTarget = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH);
$query = parse_url($_SERVER['REQUEST_URI'], PHP_URL_QUERY);
if ($query !== null && $query !== '') {
    $requestTarget .= '?' . $query;
}

if (
    $clientId === ''
    || !hash_equals($configuredClientId, $clientId)
    || !ctype_digit($timestamp)
    || abs(time() - (int) $timestamp) > 300
) {
    http_response_code(401);
    exit;
}

// Atomically reject a reused nonce, then retain it until at least (int) $timestamp + 300.
$signingKey = hash('sha256', $configuredClientSecret);
$canonical = implode("
", [
    'v1',
    $_SERVER['REQUEST_METHOD'],
    $requestTarget,
    $timestamp,
    $nonce,
    hash('sha256', $body),
]);
$expected = 'v1=' . hash_hmac('sha256', $canonical, $signingKey);

if (!hash_equals($expected, $provided)) {
    http_response_code(401);
    exit;
}

// Complete the atomic nonce check-and-store before processing the event.

1. Implement the login callback

Required. Expose an HTTPS endpoint that accepts the user's browser after authentication. The integration owner registers this endpoint's exact URL with Sorkos Auth.

GET https://client.example/auth/callback?code=<one-time-code>&state=<original-state>

Sorkos Auth redirects the browser with either code and state, or error=access_denied and state. Your endpoint must verify state against the value stored before login, reject missing or mismatched values, and exchange the code from your server at /token.

The successful token exchange returns the normalized user object and an opaque client_session_token. Store that token with the local session you create. Do not expose the client secret or perform this exchange in browser code.

This endpoint receives browser navigation, not a direct Auth-to-client server request, so it does not receive HMAC headers. Its protection comes from exact redirect-URI matching, client-generated state, the short-lived single-use code, and the authenticated server-side token exchange.

2. Check long-lived sessions when appropriate

If your project uses long-lived local sessions, optionally check their status from your server at POST /client/sessions/introspect. Send the confidential client credentials together with the client_session_token stored for that local session:

POST /client/sessions/introspect
Content-Type: application/x-www-form-urlencoded

client_id=example-id&client_secret=example-secret&client_session_token=cst_...

The response is either {"active":true} or {"active":false}. On false, immediately destroy that local session and require a new login. Treat an unknown or revoked token exactly like any other inactive token.

Choose a check interval suitable for your product. A short positive-result cache, for example 5–15 minutes, avoids a network call on every request; check immediately before especially sensitive operations if needed. Fail closed only where your availability requirements permit it.

Do not tie the local session to the central Sorkos browser cookie. That browser session has its own lifetime and may expire or be logged out while the client session remains valid. Introspection becomes inactive after explicit client-session invalidation, client disconnection, user disablement, or client disablement.

The token is only an opaque lookup identifier, not a bearer credential: Sorkos also authenticates the confidential client ID and secret, and a client can introspect only its own tokens.

3. Optionally implement session revocation

Provide this endpoint if your project can terminate every client-owned session for a given Sorkos user. Once its exact HTTPS URL is supplied to Sorkos Auth, the account page can offer the user a project-wide “Log out on all devices” action.

Sorkos Auth invalidates its own grants first, then sends this signed request:

POST /auth/sorkos/sessions/revoke
Content-Type: application/json

{"event":"logout_all","user_id":"usr_example"}

Treat user_id as the public Sorkos user ID returned during login. Invalidate all local sessions belonging to that user and return any 2xx status. The operation must be idempotent: a repeated valid request for the same user must also succeed safely.

4. Implement user deletion when supported

Provide this endpoint if your project participates in central account deletion. It must permanently remove the local account and personal data associated with the supplied public Sorkos user ID.

Sorkos Auth sends this signed request:

POST /auth/sorkos/users/delete
Content-Type: application/json

{"event":"delete_user","user_id":"usr_example"}

Make the operation idempotent and return 204 No Content once the local user and their data are absent. Central invocation is not enabled yet; implementing this contract now makes the client ready for that workflow.
